# Discovery Files: The Semantic Nervous System

## Overview

Discovery files are the semantic nervous system of our ecosystem - they tell AI systems, search engines, and crawlers who we are, what we offer, and how to interact with our content. This directory contains templates that generate discovery files for every entity in our multi-domain ecosystem.

**Build Phase**: Discovery file generation happens in Phase 5 of [builder.sh](../../BUILD.md#master-orchestrator-buildersh) (between search index generation and static site building).

**Configuration Source**: All values are injected from processed configs in `BUILD_CONFIGS_DIR/[entity]/[mode]/config.yml` (see [CONFIG.md](../../config/CONFIG.md#configuration-processing)).

**Schema Foundation**: Templates use Schema.org types defined in [schema-mappings.yml](../../config/schema/schema-mappings.yml) (see [SCHEMA.md](../../config/schema/SCHEMA.md#the-magic-of-schemaorg-integration)).

## The Discovery Suite

### 0. Search Indexes - The Content Gateway
**Standard**: FlexSearch with Schema.org aware indexing  
**Generated by**: `generate-search-index.sh` (Phase 5.0) + `generate-federated-manifest.sh` (Phase 5.1)  
**Output**: `[entity]/site/search-index.json` + `/search/` directory

Privacy-conscious, schema-aware search indexes that enable instant client-side search:
- Multi-index architecture (language, type, schema-specific)
- Progressive chunk loading for performance
- Content-based boost factors from Schema.org mappings
- Cross-domain federation via federated-manifest.json

**Integration**: Search indexes are generated BEFORE other discovery files, providing the content foundation. See [SEARCH.md](../../src/SEARCH.md) for complete implementation details.

### 1. robots.txt - The Gatekeeper
**Standard**: RFC 9309 + AI-specific extensions  
**Generated by**: `generate-robots.sh` (Phase 5.3)  
**Output**: `[entity]/site/robots.txt`

Controls crawler access with AI-specific directives. Key features:
- Distinguishes AI training (blocked) vs AI assistance (allowed)
- Domain alias support via `{{IF_DOMAIN_ALIASES}}` conditionals
- References all other discovery files via `See-Also` directives
- Entity-type specific sections (domains get federation hub references)
- Includes `/search-index.json` and `/search/` in allowed paths

**Research Driver**: [2024 AI crawler landscape](https://jemsu.com/how-should-you-handle-multi-domain-sites-and-robots-txt-for-seo-in-2024/) shows need for granular AI control.

### 2. tdmrep.json - The Legal Shield
**Standard**: [W3C TDMRep 1.0](https://w3c.github.io/tdm-reservation-protocol/spec/)  
**Generated by**: `generate-tdmrep.sh` (Phase 5.4)  
**Output**: `[entity]/site/.well-known/tdmrep.json`

Formal Text & Data Mining rights declaration following W3C ODRL format:
```json
{
  "@context": ["http://www.w3.org/ns/odrl.jsonld", "http://www.w3.org/ns/tdmrep.jsonld"],
  "@type": "Offer",
  "profile": "http://www.w3.org/ns/tdmrep"
}
```

**Legal Context**: EU AI Act (Directive 2024/1689) requires machine-readable TDM opt-out. Non-compliance risks under CDSM Articles 3 & 4.

### 3. ai.txt - The Human Bridge
**Standard**: Emerging industry practice  
**Generated by**: `generate-ai-txt.sh` (Phase 5.5)  
**Output**: `[entity]/site/ai.txt`

Human-readable AI usage policy that bridges legal requirements with practical guidance:
- Quick summary with ✅/❌ visual indicators
- Attribution examples for AI systems
- Contact hierarchy from processed configs
- Domain alias declarations

**Best Practice**: Inspired by robots.txt simplicity, provides clear guidance where tdmrep.json provides legal framework.

### 4. llms.txt - The Content Map
**Standard**: LLM content discovery (emerging)  
**Generated by**: `generate-llms-txt.sh` + `generate-llms-txt.js` (Phase 5.6)  
**Output**: `[entity]/site/llms.txt`

Two-stage generation:
1. **Shell wrapper** reads template and injects static variables
2. **JavaScript engine** analyzes actual content from `master_posts/` to add:
   - Content statistics and summaries
   - Key topics extracted from pages
   - Recent posts with timestamps
   - Project documentation summaries

**Innovation**: Unlike other discovery files, this uses content analysis to provide context, not just metadata.

### 5. ecosystem.json - The Federation Hub
**Standard**: JSON-LD 1.1 with Schema.org vocabulary  
**Generated by**: `generate-ecosystem-json.sh` (Phase 5.7)  
**Output**: `[entity]/site/ecosystem.json`

Complete federation manifest using @graph structure:
```json
{
  "@context": "https://schema.org",
  "@graph": [
    /* All entities as typed Schema.org objects */
  ]
}
```

Incorporates ALL catalogs from [ecosystem.proto](../../config/schema/ecosystem.proto):
- Legal entities, persons, brands, communities
- Complete relationship graph
- Cross-domain alias mappings
- Entity website flags for policy inheritance

**SEO Impact**: Provides complete knowledge graph for search engines, critical for multi-domain discovery.

## Variable Injection Pattern

All templates use `{{VARIABLE}}` syntax with values injected from:

1. **Processed Configs**: `BUILD_CONFIGS_DIR/[entity]/[mode]/config.yml`
   ```bash
   yq eval '.domain_info.title' "$config_path"
   ```

2. **Path Utils Functions**: Dynamic values from [path-utils.sh](../../GETHARSH.md#understanding-pathutilssh)
   ```bash
   BASE_URL=$(get_domain_url "$entity")
   ```

3. **Conditional Sections**: Entity-specific content
   ```
   {{IF_DOMAIN_ALIASES}}...{{END_IF_DOMAIN_ALIASES}}
   {{IF_ENTITY_TYPE_DOMAIN}}...{{END_IF_ENTITY_TYPE_DOMAIN}}
   ```

## Cross-Linking Architecture

Discovery files form an interconnected web where each file references others, creating multiple pathways for discovery:

```
ecosystem.json (Primary Federation Hub)
    │
    ├── @graph[] → All entities with @id references
    ├── federation.discovery → Links all discovery files
    └── entity_catalog.relationships → Complete graph
         │
         ├── search-index.json → Schema-aware content index
         │   ├── manifestUrl: /search/manifest.json
         │   ├── Multi-language indexes: en, hi, etc.
         │   ├── Type-specific indexes: posts, pages, projects
         │   └── Links to: /federated-manifest.json
         │
         ├── federated-manifest.json → Cross-domain search
         │   ├── currentDomain → This domain's capabilities
         │   └── federation.domains[] → Sister domains
         │
         ├── robots.txt
         │   ├── See-Also: /.well-known/tdmrep.json
         │   ├── See-Also: /ai.txt
         │   ├── See-Also: /llms.txt
         │   ├── See-Also: /ecosystem.json
         │   ├── See-Also: /search-index.json
         │   └── Allow: /search/
         │
         ├── tdmrep.json → ODRL policy with ecosystem references
         │   ├── dc:creator → Organization with sameAs[]
         │   └── odrl:relation → Links to policies
         │
         ├── ai.txt → Human-readable with ecosystem links
         │   └── References all domains/aliases
         │
         └── llms.txt → Content summary with federation links
             └── Federation links to parent/siblings
```

This architecture ensures that discovering ANY file leads to discovering ALL files, maximizing the chances of proper understanding by AI systems and search engines. The search indexes provide the content foundation, while other discovery files provide the policy and relationship context.

## Extension Guide

### Adding a New Discovery File

1. **Create Template** in `templates/discovery/`:
   ```
   newfile.ext.template
   ```

2. **Create Generator** in `config/tools/`:
   ```bash
   #!/opt/homebrew/bin/bash
   source path-utils.sh
   # Read template, inject variables, output to site
   ```

3. **Add to builder.sh** Phase 5:
   ```bash
   NEWFILE_TOOL="$(get_config_tool_path generate-newfile.sh)"
   "$NEWFILE_TOOL" --mode=$CURRENT_MODE || log_warning "newfile generation failed"
   ```

4. **Update build.sh** verification (Phase 6):
   ```bash
   # Check for discovery files
   if [[ ! -f "$site_dir/newfile.ext" ]]; then
       log_warning "Missing discovery file: newfile.ext"
   fi
   ```

### Adding New Variables

1. **Define in Proto** ([ecosystem.proto](../../config/schema/ecosystem.proto) or entity-specific):
   ```proto
   string new_field = N;
   ```

2. **Add to Template**:
   ```
   {{NEW_FIELD}}
   ```

3. **Extract in Generator**:
   ```bash
   new_field=$(yq eval '.path.to.new_field' "$config_path")
   ```

### Customization Points

1. **Entity-Specific Sections**: Use conditionals
   ```
   {{IF_HAS_PROJECTS}}
   Project-specific content
   {{END_IF_HAS_PROJECTS}}
   ```

2. **Dynamic Lists**: JSON arrays from discovery
   ```bash
   domains_json=$(find_all_domains | jq -c)
   ```

3. **Content Analysis**: Add to llms.txt.js engine
   ```javascript
   // Analyze specific content patterns
   const expertise = analyzeExpertiseAreas(pages);
   ```

## Maintenance Notes

### Regular Updates

1. **Standards Evolution**: Monitor W3C TDMRep, Schema.org updates
2. **AI Crawler Changes**: Update robots.txt user agents quarterly
3. **Legal Compliance**: Review TDM policies with EU AI Act changes

### Testing Checklist

- [ ] Validate JSON-LD with [Google's Rich Results Test](https://search.google.com/test/rich-results)
- [ ] Check TDMRep format with W3C validator (when available)
- [ ] Test robot.txt with crawler simulators
- [ ] Verify all cross-references resolve correctly
- [ ] Confirm variable substitution has no `{{VARIABLE}}` remnants

### Common Issues

1. **Missing Variables**: Check processed config has the field
2. **Invalid JSON**: Often missing commas in JSON arrays
3. **Broken References**: Ensure @id matches across files
4. **Alias Confusion**: Canonical URL must be consistent

## Design Philosophy

Following [GETHARSH.md](../../GETHARSH.md#the-philosophy) principles:

1. **Pattern-Based**: No hardcoding, everything discovered
2. **Single Source of Truth**: Templates + processed configs
3. **Ecosystem Aware**: Every file knows its place in the whole
4. **Future Proof**: Extensible without breaking changes
5. **Machine & Human**: Readable by both audiences

## Impact on Final Bundle

As documented in [BUILD.md](../../BUILD.md#build-sequence), discovery files are generated in Phase 5 and become part of the static bundle:

```
[entity]/site/
├── index.html                 # Gatsby output
├── search-index.json          # Search Phase 5.0
├── federated-manifest.json    # Search Phase 5.1 (if enabled)
├── robots.txt                 # Discovery Phase 5.3
├── ai.txt                     # Discovery Phase 5.5
├── llms.txt                   # Discovery Phase 5.6
├── ecosystem.json             # Discovery Phase 5.7
├── manifest.json              # Manifest Phase 3
├── search/                    # Search index chunks
│   ├── manifest.json          # Index manifest with languages
│   ├── documents-chunk-0.json # Progressive loading chunks
│   ├── en-unified-index.json  # Language-specific index
│   └── ...                    # Additional indexes
└── .well-known/
    └── tdmrep.json           # Discovery Phase 5.4
```

These files enable:
- **Content Search**: Via search-index.json and FlexSearch
- **Cross-Domain Search**: Via federated-manifest.json
- **Search Discovery**: Via robots.txt and sitemaps
- **AI Interaction**: Via ai.txt and llms.txt
- **Legal Compliance**: Via tdmrep.json
- **Federation**: Via ecosystem.json
- **Knowledge Graph**: Via Schema.org in all files

## Search Integration Details

### Search Index Generation (Phase 5.0-5.1)

The search system generates discovery files that enable instant, privacy-conscious search:

1. **search-index.json** - Entry point with metadata
   - Links to manifest and chunks
   - Statistics about content
   - Generated by: [`generate-search-index.js`](../../config/tools/generate-search-index.js)

2. **search/manifest.json** - Index orchestration
   - Language indexes (en, hi, etc.)
   - Type indexes (posts, pages, projects)
   - Specialized schema indexes
   - Chunk information for progressive loading

3. **federated-manifest.json** - Cross-domain search
   - Maps sister domains in ecosystem
   - Enables unified search experience
   - Generated by: [`generate-federated-manifest.js`](../../config/tools/generate-federated-manifest.js)

### Schema-Aware Search Features

- **300+ Proto-to-Schema.org mappings** drive intelligent tokenization
- **Multi-index architecture** optimizes for different content types
- **Content-based boost factors** improve relevance
- **Progressive chunk loading** ensures fast initial load
- **Privacy-conscious** - respects consent and draft status
